# Findings

What actually happened moving 250,000 payment transactions from SQL Server 2022 to
PostgreSQL 15 on AWS RDS.

Every number below came out of a real run. Nothing here is from documentation.

---

## The headline

**The migration was perfect. The reports were wrong anyway.**

```
Legacy query returned      125,504 rows
Migrated query returns      41,612 rows
Silently no longer matched  83,892 rows  (66.8%)
```

Every row arrived. Every value is byte-identical. All 15 verification checks pass. And
`WHERE txn_status = 'Captured'` returns a third of what it used to.

SQL Server's default collation is case-**in**sensitive, so that clause matched `Captured`,
`captured` and `CAPTURED` alike. PostgreSQL is case-**sensitive**, so it matches one of them.

No error. No warning. Nothing to grep for in a log. A settlement report just gets quieter,
and it stays quiet until somebody reconciles against the bank.

**This is the class of failure the project exists for**, and it is not fixable by re-running
the migration — see [Remediation](#remediation) below.

## Type mapping, and what each one actually costs

| SQL Server | PostgreSQL | What goes wrong if you get it wrong |
|---|---|---|
| `IDENTITY(1,1)` | `GENERATED BY DEFAULT AS IDENTITY` | Sequence stays at 1 after a keyed load. First real insert collides |
| `UNIQUEIDENTIFIER` | `uuid` | SQL Server stores the first three fields little-endian; Postgres is big-endian. Moving raw bytes scrambles it. Migrate the **string** form |
| `NVARCHAR(n)` | `text` | Nothing, if the encoding survives the load. See failure 8 |
| `CHAR(n)` | `char(n)` | Trailing-space comparison semantics differ. Kept as-is deliberately: changing it mid-migration means you can no longer tell a bug from an intended fix |
| `BIT` | `boolean` | Every query comparing to `0`/`1` breaks. A code change no data check will find |
| `MONEY` | `numeric(19,4)` | **Never `float`. Never Postgres's own `money`** — it is locale-dependent and its scale comes from a server parameter. And not `numeric(19,2)`: `MONEY` carries four decimals |
| `DATETIME2` | `timestamptz` | Carries no timezone. Guess the offset wrong and every date near midnight moves to a different day |
| Default collation | *(case-sensitive)* | **The expensive one.** Query results change with no error |
| Clustered index | *(no equivalent)* | `CLUSTER` is a one-time reorder that decays. Range scans behave differently after migration |
| Computed column `PERSISTED` | `GENERATED ALWAYS ... STORED` | Postgres requires immutability. Anything using `GETDATE()` or a user function will not convert — it needs a trigger or a view |
| Stored procedure | PL/pgSQL function | Does not convert. Gets rewritten — and rewriting is where the collation bug surfaced |

## The eight failures

Every one of these came from running the thing, not reading about it.

### 1. The AWS account type blocked the build

```
InvalidParameterCombination: The specified instance type is not eligible for Free Tier.
FreeTierRestrictionError: The specified backup retention period exceeds the maximum
                          available to free tier customers.
```

Not a quota — an **account type**. The AWS Free Plan permits only free-tier-eligible
instance types and caps backup retention outright.

`c7i-flex.large` turned out to be eligible: 2 vCPU, 4 GB, x86. More headroom than the
`t3.medium` originally chosen. The constraint produced a better answer than the default did.

### 2. A primary key is clustered by default

```
Msg 1902: Cannot create more than one clustered index on table 'dbo.transactions'.
```

SQL Server makes the PK clustered unless told otherwise, and a table can have only one.
Clustering on `captured_at` instead — which is what a real payments schema does, because
settlement reports scan by date all day — requires declaring the PK `NONCLUSTERED`.

It is also precisely what does not survive: PostgreSQL has no maintained clustered index.

### 3. `QUOTED_IDENTIFIER` is required for computed columns

```
Msg 1934: CREATE TABLE failed because the following SET options have incorrect
          settings: 'QUOTED_IDENTIFIER'.
```

`sqlcmd` does not set it. Any statement touching a table with a computed column needs it —
including a plain `DELETE`. The error names the SET option, not the table, which sends you
looking in the wrong file.

### 4. Drop order, and a misleading error

Dropping `merchants` before `transactions` fails on the foreign key. The drop failing then
makes the `CREATE` report *"There is already an object named 'merchants'"* — which points at
the create, not the drop. Children before parents.

### 5. The Docker volume survived `docker rm`

The rebuild looked idempotent and was not. A named volume outlives the container, so every
run inherited the previous run's tables.

This is how a stale schema gets blamed on a migration bug. Cost more time than any other
failure here, because everything *looked* right.

### 6. `SET IDENTITY_INSERT` does not apply to `BULK INSERT`

```
Msg 545: Explicit value must be specified for identity column in table 'merchants'
```

Bulk load needs its own `KEEPIDENTITY`. Worse, the two together are actively dangerous: when
a `BULK INSERT` fails, the matching `SET IDENTITY_INSERT ... OFF` never runs, and the next
table's `ON` fails with *"IDENTITY_INSERT is already ON for table X"*.

One broken statement silently broke every load after it, and four cascading errors buried
the one that mattered. Every table read zero rows when a single statement had failed.

### 7. The verification tool was lying about precision

```
SQL Server   1410439927.94
PostgreSQL   1410439927.9439
```

`CAST(money AS VARCHAR)` rounds to **two** decimals. `MONEY` stores **four**. The baseline
was truncating the measurement, not the data — `.9439` rounds to `.94`, and the values were
identical all along.

The tempting fix is to round both sides to 2dp so they agree. **That is the worst possible
move**: it permanently blinds the check to a real 4-decimal truncation, which is the single
most expensive mistake available in this migration.

> A measurement has to be at least as precise as the thing it measures, or it is not a
> measurement.

### 8. `BULK INSERT` on Linux cannot read UTF-8, and fails silently

```
file:      北方物流 Equipment Rental
database:  σîùµû╣τë⌐µ╡ü Equipment Rental
```

`CODEPAGE = '65001'` is how you tell SQL Server a file is UTF-8. That option **does not exist
on Linux**. Dropping it and assuming UTF-8 is read natively loaded the bytes one at a time as
a single-byte codepage. Nothing errored.

Getting to the working version took three more precise failures:

- `iconv -t UTF-16LE` writes no byte order mark, and `BULK INSERT` rejects widechar without
  one — *"the data file does not have a Unicode signature"* — then **falls back to char,
  mangles it, and continues**. `iconv -t UTF-16` writes the mark.
- `FORMAT = 'CSV'` cannot be combined with `DATAFILETYPE`.
- With `widechar`, the terminators are wide too.

**And this is the one worth remembering:**

**Thirteen of fourteen checks passed over that corrupted data.** Row counts, money sums,
date ranges, null counts, per-merchant totals — all green. The migration itself was flawless:
it carried the mojibake across perfectly, so source and target matched exactly.

> A suite that only diffs two databases can prove the move was faithful.
> It can never prove the thing being moved was right.

Hence `test_source_database_matches_the_original_file`, anchored to the seed file, outside
both systems. Somewhere the chain has to touch ground.

### Bonus: the source database could not describe its own data

```
SQL Server   {'captured': 125504}
PostgreSQL   {'captured': 41682, 'CAPTURED': 42210, 'Captured': 41612}
```

`41,682 + 42,210 + 41,612 = 125,504` exactly.

Under a case-insensitive collation, `GROUP BY` **merges** the variants and labels the group
with whichever spelling it met first. SQL Server reported one distinct status where three
exist. The profiler had to force `COLLATE ... _CS_AS` to ask the question it actually meant.

A verification tool that inherits the source system's blind spots will confirm whatever the
source believes about itself.

## Remediation

When verification fails, what you do depends on which class of failure it is. Getting this
wrong is worse than the original bug.

| Class | Symptom | Response |
|---|---|---|
| **0** | Source disagrees with the original file | The data was wrong before migration. Fix ingestion, reload the source, start over |
| **1** | Rows missing | Load died partway. Fix, **wipe**, reload |
| **2** | Values differ | Type mapping bug. Fix the mapping, **wipe**, reload |
| **3** | Same rows, same values, **different query results** | Not a data bug. **Reloading will never fix it** |

**Never fix forward on the target.** The instinct is to patch the missing rows by hand. Do
not: you then have a database that matches nothing, cannot be reproduced, and cannot be
proven. That is why the load is idempotent — the correct response to a failure is always to
fix the pipeline and reload from scratch.

**The source stays authoritative and live** throughout. That is the real reason DMS CDC
matters: the legacy system keeps accepting writes while you sort it out, so a failed
verification costs time rather than transactions.

### Remediating the collation finding specifically

It is class 3. The data is provably intact, so there is nothing to reload. It needs a
decision, and the decision belongs to the business, not the migration:

| Option | Cost | Risk |
|---|---|---|
| `citext` extension on the column | One migration. Queries unchanged | Non-standard type; indexes behave differently |
| `lower()` with a functional index | Explicit, standard, indexable | Every query has to be found and changed |
| Normalise the data + `CHECK` constraint | Cleanest end state | Destroys the original values. Needs sign-off |
| Change nothing, accept new semantics | Free | Reports silently change. Almost never correct |

Deliberately **not** applied during the load. Quietly normalising the case would have hidden
the finding — and hiding it is how it reaches production. It belongs in a follow-up
migration, applied knowingly, by someone who chose it.

## What has no equivalent on the other side

- **SQL Server Agent.** RDS PostgreSQL has no job scheduler. Every scheduled job has to be
  rebuilt — `pg_cron`, Lambda + EventBridge, or Airflow. The most commonly forgotten step
  after the tables are across.
- **Clustered indexes.** `CLUSTER` is a one-time reorder that decays and takes an exclusive
  lock. Range-scan performance genuinely changes.
- **Stored procedures.** Rewritten, not converted.
- **Case-insensitive default collation.** The subject of this entire document.

## Operations

### Recoverability, measured

```
snapshot        196s   (3m 16s)
restore         515s   (8m 35s)   ← this is the number that matters
verification    PASSED  row counts and money sums match the live instance
total           716s   (11m 56s)
```

**Recovery from an existing snapshot: about 9 minutes** for 250,000 rows on a
`db.t4g.micro`. That is a measured RTO. Every other number in a recovery conversation is
someone's estimate.

Two things worth separating:

- **Snapshot time is not recovery time.** The snapshot is the cheap half. Restore took 2.6×
  longer, and restore is the half that happens during an incident.
- **The verification step is what makes it a proven backup.** The drill queries the restored
  copy and compares it to the live one. A snapshot that restores into a database nobody
  queried is a file, not a recovery plan.

Scale caveat: restore time grows with data volume and shrinks with instance class. Nine
minutes here says nothing about nine minutes at 25 million rows — which is exactly why the
drill is a script that can be re-run rather than a number written down once.

### The scheduled job that has no equivalent

RDS PostgreSQL has **no SQL Server Agent**. No scheduler, no job history, no failure
alerting. And nothing in a schema comparison will report a missing job, because a job was
never part of the schema.

Rebuilt with `pg_cron`:

```
jobid  schedule      jobname                    active
1      15 6 * * *    daily_settlement_summary   true

job wrote 12,118 summary rows
job_run_log: succeeded
```

Three details that are easy to get wrong:

- **`pg_cron` schedules in UTC**, regardless of the server's timezone. One more place a
  settlement can land on the wrong day.
- **On RDS it needs `shared_preload_libraries` and a reboot.** Not a runtime `CREATE
  EXTENSION`. Worth discovering before the migration rather than during it.
- **It runs on the writer only.** Correct here, and a trap after a Multi-AZ failover if the
  job assumes it is the only copy running.

The job is **idempotent by upsert**, because a scheduled job will run twice eventually — a
retry, a manual re-run after an incident, a failover replaying it. One that doubles its
numbers on a second run is a liability.

And it uses `lower(txn_status)` with a matching functional index. That is the collation
remediation, applied deliberately at the one place it is needed, rather than by quietly
rewriting the data.

## AWS DMS: six failures to reach a working task

The manual migration is how you learn what is happening. DMS is what a real cutover uses,
and the difference is not speed — it is that the source never stops accepting writes.

**The result:**

```
full load               60s        250,000 transactions
CDC replication lag     3.0s       measured, not estimated

  inserted txn_id 250001 on SQL Server  00:50:55Z
  arrived in PostgreSQL                 00:50:58Z
  amount 7834.4321 — four decimals intact
```

Getting there took six failures, and they are worth listing because the first five all
produce error messages that point somewhere other than the cause.

### 1. `dms.t3.micro` does not exist

```
InvalidParameterValueException: Invalid ReplicationInstance class
```

AWS retired it. The error does not say what *is* valid.
`aws dms describe-orderable-replication-instances` is the authority. `dms.t3.small` is the
smallest that remains.

### 2. Non-ASCII in a description field

```
The parameter ReplicationSubnetGroupDescription must not contain
non-printable control characters.
```

An em-dash. DMS wants ASCII in that field.

### 3. DMS rejects passwords that RDS accepts

```
The parameter Password contains at least one unsupported characters
from following list : ;+%
```

RDS took the same password without complaint. The generated charset now has to be the
**intersection** of what SQL Server, DMS and a shell all accept, with length carrying the
entropy instead.

### 4. The CDC mechanism is chosen from the LOGIN

```
The MS SQL Server instance is not set up for Replication.
The Distributor has not been installed correctly.
```

DMS has two ways to read changes from SQL Server:

| | Requires |
|---|---|
| **MS-REPLICATION** | A configured Distributor — full transactional replication infrastructure |
| **MS-CDC** | CDC enabled on the database and tables |

**And you do not choose directly.** DMS decides from the privileges of the connecting
account: `sysadmin` gets MS-REPLICATION, anything else gets MS-CDC.

Connecting as `sa` therefore forced the wrong mechanism, and no connection attribute could
override it — the decision was made before any attribute was read.

So the fix for the failure and the fix for the security problem were the same fix. A
dedicated non-sysadmin `dms_user`. DMS should never have been connecting as `sa`.

**And a genuine irony:** CDC on SQL Server is implemented as **SQL Server Agent jobs**. The
Agent — the thing PostgreSQL has no equivalent of, the thing this migration replaces with
`pg_cron` — has to be switched *on* before the migration can happen at all. Without it the
capture tables stay empty while everything reports success.

### 5. `setUpMsCdcForTables` means "set CDC up FOR me", not "use CDC"

```
Only members of the sysadmin fixed server role can perform this operation.
```

The attribute looked like the missing piece. It instructs DMS to run `sp_cdc_enable_table`
itself, which needs exactly the sysadmin privilege that had just been removed on purpose.

CDC was already enabled. The attribute was not merely unnecessary — it was fatal.

### 6. The fix is named only in the task log

```
Ignore_Ms_Replication_Enablement is set to 'false'
The MS SQL Server instance is not set up for Replication.
Database instance is not enabled for REPLICATION: Applying enablement...
  -> Only members of the sysadmin fixed server role can perform this operation
```

Even on the MS-CDC path, DMS checks whether the instance is configured for replication and,
finding it is not, **tries to enable it** — requiring the privilege deliberately removed to
get onto the MS-CDC path in the first place.

`IgnoreMsReplicationEnablement=true` stops it. That name appears in the task log and not in
the endpoint documentation.

**How it was found matters more than the flag.** Not by searching, but by reading the log
line by line. The error names a privilege. The line above it names the cause. The line above
*that* names the setting.

### And one more: a LOGIN is not a USER

```
The SELECT permission was denied on the object 'fn_dblog',
database 'mssqlsystemresource', schema 'sys'.
```

DMS's own row validator reads the transaction log directly, which `db_owner` and
`VIEW SERVER STATE` do not cover. Granting it failed with *"Cannot find the user
'dms_user'"* — because a **login** is server-level and a **user** is database-level, and
creating one does not create the other. That message reads like the login failed to create,
which it had not; it had been verified two lines earlier by connecting as it.

## Performance: the index did not help, and that is the finding

```
before   14.7 ms    Aggregate -> Bitmap Heap Scan -> Bitmap Index Scan
after    14.5 ms    same plan shape
                    1.0x
index size          12 MB against a 24 MB table
```

A covering index on `(captured_at, lower(txn_status)) INCLUDE (merchant_id, amount)` bought
0.2 milliseconds.

The existing btree on `captured_at` already answered the query, and **buffers read was 0
before the change** — the working set is cached, so there was no I/O to save.

**An index that does not help is not free.** It is written on every INSERT, UPDATE and
DELETE, it enlarges every backup, and it competes for the same cache that was making the
query fast. On a table taking payment traffic that is a real cost for no benefit.

The honest action is to drop it.

> Reporting this as a win would have been easy — quote best-of-N instead of the median and
> 14.4 vs 14.5 becomes a number you can put in a slide. It would also have left 12 MB of
> write amplification in production. The script now says so explicitly whenever the speedup
> is under 1.2x.

The migration-specific point underneath: the source table was **CLUSTERED** on `captured_at`,
so range scans read physically sequential pages and stayed that way. PostgreSQL has no
maintained clustered index. At a data size that no longer fits in cache, this same query
behaves differently on the two engines, and no row count or checksum would show it.

## The analytics path

```
2026-11-01     7,561 rows    177 KB
2026-08-29       928 rows     33 KB
2026-08-28       996 rows     35 KB
2026-08-27       975 rows     34 KB
2026-08-26       926 rows     32 KB

11,386 rows in 0.3 MB Parquet
s3://.../payments/transactions/capture_date=YYYY-MM-DD/
```

Hive-partitioned Parquet, which Snowflake reads through an external stage with no
Snowflake account needed to make the shape real.

The line that matters is the schema: `amount` is declared `decimal128(19,4)` explicitly.
Arrow's default inference for a Postgres `numeric` can land on `float64`, which would
reintroduce the exact error the rest of this project exists to detect. Money stays exact end
to end or the pipeline is not trustworthy.

**This is a different problem from the migration**, and both are in the job description. RDS
answers thousands of small reads and writes per second. This answers "sum a quarter."

*(The 7,561 rows on 2026-11-01 are the DST-boundary cluster the generator plants
deliberately.)*

## What a migration cannot fix

- **RDS Proxy is unavailable on AWS Free Plan accounts.** The configuration is complete and
  correct and sits behind a flag defaulting to off. A billing restriction, not a design gap.
- **The collation semantics.** Covered above — a decision, not a reload.
- **The clustered index.** No PostgreSQL equivalent exists.

## What would be different at 100× the data

This moved 250,000 rows in 14 seconds with the source offline. At 25 million with the source
live, everything changes:

- **`executemany` stops being viable.** `COPY` from a stream, or DMS.
- **The cutover is the hard part, not the copy.** DMS full-load plus CDC so the source keeps
  taking writes; cut over only once replication lag is near zero.
- **Verification has to run against a moving target.** Compare as of a timestamp, or freeze
  writes briefly and compare then.
- **Per-merchant checksums get expensive.** Sample, or checksum by partition.
- **Rollback has to be real.** Keep the source readable and writable until the new system has
  survived a full settlement cycle.
- **Indexes are built after the load, not before.** Loading into an indexed table is far
  slower than loading and then indexing.
